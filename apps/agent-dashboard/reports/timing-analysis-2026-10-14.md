## ข้อเสนอแนะ (เรียงตามเวลาที่น่าจะประหยัดได้)

ตัวเลข "ประหยัดได้" เป็นสถานการณ์สมมติ คำนวณจากข้อมูลข้างบน ไม่ใช่ผลที่วัดได้

1. **ลด Dev run ยาว: แตก brief เป็นก้อนเล็กที่มีเกณฑ์จบชัด (ประหยัดมากสุด)**
   - ข้อมูล: Dev run เกิน 10 นาที 18 ครั้ง = 5h28m (45% ของเวลา agent) โดย 7 ตัวเกิน 20 นาที (2h54m) บาง brief รวมหลายเรื่อง ("fix + commit", "effects + flaky fix", "visual overhaul")
   - ทำ: ให้ Dev ทำทีละ milestone พร้อม acceptance criteria และตัดเรื่อง "commit/แก้ผล review" ออกเป็น run แยกที่สั้นกว่า; สั่ง run ยาวแบบ async (30 จาก 37 run ที่เกิน 5 นาทีเป็น sync) เพื่อให้เลขายังตอบเจ้าของได้และเปิด QA คู่ขนานได้
   - สมมติถ้าลด run เกิน 10 นาทีลงได้ 20% -> ประหยัด ~66 นาทีใน 4 วัน (19,701s x 0.2)
   - ลองด้วย: ทดสอบ effort ของ Dev (ตอนนี้ sonnet/high) เทียบ medium กับงานประเภทเดียวกัน ในเอกสารส่งต่องานภายในระบุว่ายังไม่ได้ทดสอบว่า effort ใน frontmatter ของ subagent มีผลหรือไม่ และ log นี้ไม่บันทึก model/effort ต่อ run จึงยังสรุปจากข้อมูลนี้ไม่ได้ว่าลด effort แล้วเร็วขึ้นเท่าไร

2. **ตัดช่วง idle ระหว่าง QA -> Dev และ Dev -> Dev ด้วย fix-loop ที่อนุมัติล่วงหน้า**
   - ข้อมูล: 59 + 57 handoffs รวม 4h43m (มัธยฐาน 78-88s, p90 6-7 นาที) ส่วนใหญ่เป็น idle
   - ทำ: เจ้าของกำหนดกฎล่วงหน้า เช่น "ข้อ Must-fix/Low ที่ QA ระบุ ให้เลขาส่ง Dev แก้แล้วส่ง QA ตรวจซ้ำได้เลยไม่ต้องรอถาม" ให้เลขาหยุดถามเฉพาะเรื่องที่ต้องตัดสินใจจริง (เปลี่ยน scope, ลบไฟล์, เรื่อง public)
   - สมมติถ้าลดช่วงรอ 30% -> ประหยัด ~85 นาที (4h43m = 16,984s x 0.3) แต่ส่วนที่เป็นเวลาอ่านรายงานของเจ้าของเป็นเวลาที่ควรเก็บไว้ จึงเป็นเพดานสูง
   - ต้องให้เจ้าของยืนยันเรื่องนี้ก่อน เพราะเปลี่ยนจุดควบคุมของมนุษย์

3. **ขนานงานที่แยกไฟล์/ขอบเขตกันได้ และให้ QA ตรวจชิ้นก่อนหน้าไปพร้อมกับ Dev ทำชิ้นถัดไป**
   - ข้อมูล: ซ้อนกันจริงแค่ 4m56s; มี 18 คู่ run ที่ทั้งคู่ยาวเกิน 60s และ role เดียวกัน เพดานทางทฤษฎี ~81 นาที แต่น่าจะชนกันหลายคู่ (ไฟล์ชุดเดียวกัน)
   - ทำ: ให้เลขาระบุไฟล์/โฟลเดอร์ที่แต่ละ run แตะใน brief แล้วเปิดคู่ขนานเมื่อไม่ทับกัน
   - ประหยัดจริงน่าจะต่ำกว่าเพดานมาก (ประเมินเป็นตัวเลขไม่ได้จาก log นี้)

4. **ปรับปรุงการเก็บ log ก่อนปรับแต่งรอบหน้า (ไม่ลดเวลาตรง ๆ แต่ทำให้ #1-#3 ตรวจผลได้)**
   - เพิ่มใน event: model + effort ต่อ run, จำนวน tool call ต่อ run, แยก UserPromptSubmit ของมนุษย์ออกจาก task-notification, log tool ใน subagent ให้ครบ, และ task/chain id ที่เลขาใส่ตอนสั่งงาน

5. **ไม่ต้องแก้ (ตรวจแล้วไม่ใช่คอขวด)**
   - relay ของเลขา: ~9s ต่อ handoff (1.7% ของเวลาจริง)
   - run จิ๋วที่สั้นกว่า 10s (39 จาก 274): ตรวจรายชื่อแล้ว ส่วนใหญ่เป็น run ทดสอบ/เดโมที่ตั้งใจทำ (เช่น "Delegation test to ...", "Dashboard test: ...", "Demo: ...") ไม่ใช่ความสิ้นเปลืองของงานจริง
   - QA: เฉลี่ย 1m24s และ Dev -> QA ส่งต่อใน 12s อยู่แล้ว ไม่มีอะไรให้ตัดเพิ่ม

## ข้อจำกัดของข้อมูล (อย่าอ่านตัวเลขเกินจริง)

- **ไม่มี event "งานจบ" ที่ผูกกับ task**: ไม่มี task id/chain id ใน log ต้องเดา chain จากระยะห่าง 10 นาที (เปลี่ยนได้ด้วย `--chain-gap`) การตัดต่างกันจะให้ตัวเลข chain ต่างกัน
- **แยก idle ของเจ้าของ กับ idle ที่ไม่ทราบสาเหตุไม่ได้**: UserPromptSubmit ไม่บอกว่ามนุษย์หรือระบบส่ง ใช้กฎ "prompt ภายใน 2s หลัง run จบ = task-notification" ซึ่งเป็น heuristic
- **ไม่บันทึก model/effort ต่อ run**: และ frontmatter ของ agent เปลี่ยนไประหว่างช่วง log จึงจับคู่ผลกับ effort ไม่ได้
- **log tool ใน subagent ไม่ครบ**: เช่น Edit มีแค่ 2 รายการ ตัวเลขเวลา tool เป็นขอบล่าง
